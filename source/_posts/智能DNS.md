# 第一章：背景与核心问题

## 1.1 业务场景

您的公司在中国境内部署了核心服务（Web 应用、API、内部系统等），同时有大量来自全球各地的用户或合作伙伴需要访问这些服务。由于中国独特的网络环境，海外用户直连中国服务器面临以下典型问题：

| 问题 | 原因 |
|------|------|
| 高延迟（300ms～2000ms） | 跨境物理距离 + 国际出口带宽拥塞 |
| 丢包率高 | 国际互联网与中国网络之间的互联点（IX）承载量有限 |
| 访问不稳定 | 中美/中欧之间路由路径不固定，受网络抖动影响 |
| 体验差 | 动态内容无法被传统 CDN 缓存，延迟问题直接暴露给用户 |

## 1.2 解决思路：全球加速 + 就近接入

供应商提供的"全球加速"方案，核心逻辑是：

> **让全球用户就近接入供应商在当地的 PoP（接入节点），再通过供应商的高质量私有骨干网络，将流量"回传"到中国内地的您的源站服务器。**

这本质上是将"跨越劣质公网"的问题，转换为"借用供应商的高质量专网"来解决。

```
【传统访问路径 - 高延迟】
海外用户 ──── 公网国际链路（拥塞、抖动） ──── 中国源站

【全球加速路径 - 低延迟】
海外用户 ──── 就近 PoP 节点 ──── 供应商骨干专网 ──── 中国源站
              （低延迟接入）      （高质量私有链路）
```

## 1.3 为什么需要 CNAME？

这是许多客户最困惑的地方。要实现"就近接入"，核心挑战是：**不同地区的用户需要连接到不同地区的 PoP 节点**，这就需要一种机制来动态地、按地理位置地将用户"引导"到正确的节点。

CNAME（Canonical Name，规范名称）配合智能 DNS 正是实现这一引导的核心机制：

- 您的内网 DNS 将 `your-app.corp.com` CNAME 到 `your-account.vendor-cdn.com`
- 当任何人解析 `your-app.corp.com` 时，最终会问到供应商的 DNS 服务器
- 供应商的 DNS 服务器知道这个请求来自哪里（地理位置），返回最近的 PoP 节点 IP

这一机制的完整原理将在后续章节展开。

# 第二章：DNS 基础——一次解析请求的完整生命周期

## 2.1 DNS 是什么

DNS（Domain Name System，域名系统）是互联网的"电话薄"，负责将人类可读的域名（如 `www.example.com`）翻译成计算机可路由的 IP 地址（如 `203.0.113.1`）。

DNS 是分布式、层次化的系统，由以下几类角色协同工作：

| 角色 | 职责 | 示例 |
|------|------|------|
| 根域名服务器（Root NS） | 知道所有 TLD 的位置 | 全球 13 组，由 IANA 管理 |
| 顶级域服务器（TLD NS） | 知道 .com/.cn/.net 下各域名的 NS | Verisign 管 .com |
| 权威域名服务器（Authoritative NS） | 持有某个具体域名的最终记录 | 你在域名注册商配置的 NS |
| 本地递归解析器（Recursive Resolver） | 代表用户做完整的解析查询 | 运营商 DNS、8.8.8.8、114.114.114.114 |
| 客户端 DNS 缓存 | 操作系统/浏览器层面的短期缓存 | Windows DNS Cache Service |

## 2.2 标准递归解析流程

以解析 `app.corp.com` 为例，一次完整的 DNS 递归解析过程：

```
步骤 1: 客户端检查本地缓存
  ├─ 命中缓存 → 直接使用（跳过后续步骤）
  └─ 未命中 → 向本地递归解析器（Local DNS）发起查询

步骤 2: 本地递归解析器检查自身缓存
  ├─ 命中缓存 → 直接返回给客户端
  └─ 未命中 → 开始递归查询

步骤 3: 递归解析器问根服务器
  递归器 → 根服务器: "谁管 .com？"
  根服务器 → 递归器: ".com 的 NS 是 a.gtld-servers.net"

步骤 4: 递归解析器问 TLD 服务器
  递归器 → a.gtld-servers.net: "谁管 corp.com？"
  TLD NS  → 递归器: "corp.com 的 NS 是 ns1.your-registrar.com"

步骤 5: 递归解析器问权威服务器
  递归器 → ns1.your-registrar.com: "app.corp.com 的 IP 是多少？"
  权威NS  → 递归器: "app.corp.com 是 A 记录 1.2.3.4，TTL=300"

步骤 6: 递归解析器返回结果给客户端
  递归器 → 客户端: "app.corp.com = 1.2.3.4"
  （递归器缓存此结果 300 秒）

步骤 7: 客户端发起 TCP/UDP 连接到 1.2.3.4
```

## 2.3 关键 DNS 记录类型

| 记录类型 | 用途 | 示例 |
|---------|------|------|
| **A 记录** | 域名 → IPv4 地址（最终结果） | `app.corp.com → 1.2.3.4` |
| **AAAA 记录** | 域名 → IPv6 地址 | `app.corp.com → 2001:db8::1` |
| **CNAME 记录** | 域名 → 另一个域名（别名） | `app.corp.com → app.vendor-cdn.com` |
| **NS 记录** | 指定域名的权威服务器是谁 | `corp.com NS ns1.registrar.com` |
| **MX 记录** | 邮件服务器地址 | `corp.com MX mail.corp.com` |
| **TXT 记录** | 任意文本，用于 SPF/验证等 | `corp.com TXT "v=spf1 ..."` |

## 2.4 TTL（生存时间）的作用与影响

每条 DNS 记录都有 TTL（Time To Live，单位：秒），告诉缓存"这条记录最多保存多久"。

```
TTL = 300  → 缓存 5 分钟，5 分钟后必须重新查询
TTL = 3600 → 缓存 1 小时
TTL = 86400 → 缓存 1 天
```

**TTL 对全球加速的影响：**

- **TTL 过长**：当某个 PoP 节点故障时，用户在 TTL 过期前仍会被解析到故障节点，体验差。
- **TTL 过短**：DNS 查询频率大增，压力落到 GSLB 系统上（但 GSLB 可以借此更精准地调度）。
- **供应商通常建议 TTL = 60～300 秒**，在切换灵活性和查询压力间取得平衡。

## 2.5 CNAME 链式解析

当存在 CNAME 时，解析器会继续追踪，直到找到最终的 A 记录：

```
app.corp.com      CNAME → app.vendor-cdn.com
app.vendor-cdn.com CNAME → pool-asia.gslb.vendor.com   （供应商内部）
pool-asia.gslb.vendor.com  A → 203.0.113.50            （最终 IP）
```

客户端收到的是最终的 A 记录 IP，对 CNAME 链是透明的。整个链条的解析发生在 DNS 层面，客户端无感知。

## 2.6 EDNS Client Subnet（ECS）扩展

传统 DNS 的问题：递归解析器发给权威 DNS 的请求，只有递归解析器自己的 IP，而非真实用户的 IP。

```
真实用户 IP: 202.100.1.1（中国广州电信用户）
本地 DNS IP: 8.8.8.8（Google DNS，位于美国）

传统情况：GSLB 以为用户在美国，返回美国 PoP 的 IP → 错误调度
```

**EDNS Client Subnet（ECS，RFC 7871）**解决了这个问题：递归解析器在 DNS 查询中附带用户 IP 的前缀（如 `202.100.0.0/24`），权威 DNS（GSLB）可据此准确判断用户位置：

```
递归解析器 → 权威 DNS:
  Query: app.vendor-cdn.com
  EDNS Option: client-subnet=202.100.0.0/24  ← 用户 IP 前缀

权威 DNS → 递归解析器:
  Answer: 203.0.113.50  ← 距离广州最近的 PoP 节点
```

主流 CDN 供应商（阿里云、腾讯云、Cloudflare、Akamai 等）的 GSLB 均支持 ECS，以实现更准确的地理调度。

# 第三章：智能 DNS（GeoDNS）原理

## 3.1 什么是智能 DNS

智能 DNS（也称 GeoDNS、Geo-aware DNS）是在标准 DNS 基础上增加了**地理感知**和**条件路由**能力的权威 DNS 服务。普通权威 DNS 对所有人返回同一个 IP，而智能 DNS 会**根据查询来源的 IP 地址（地理位置、网络运营商、ASN 等维度）返回不同的 IP 地址**。

```
普通 DNS：
  任何人查询 app.corp.com → 返回 1.2.3.4

智能 DNS：
  来自欧洲的查询    → 返回 151.0.1.1  （欧洲 PoP）
  来自北美的查询    → 返回 104.0.1.1  （北美 PoP）
  来自东南亚的查询  → 返回 43.0.1.1   （新加坡 PoP）
  来自中国的查询    → 返回 123.0.1.1  （国内节点/源站）
```

## 3.2 智能 DNS 的核心数据：IP 地理库

智能 DNS 的核心是一个**高精度 IP 地理信息数据库**，它将全球每个 IP 段映射到：

- 国家 / 地区
- 省份 / 州
- 城市
- ISP / 运营商（如中国电信、联通、移动）
- ASN（自治系统号）

供应商通常从多个来源维护这个库：

| 数据来源 | 说明 |
|---------|------|
| MaxMind GeoIP2 | 商业 IP 地理数据库，行业标准 |
| RIPE / APNIC / ARIN Whois | 各地区互联网注册机构的 IP 分配记录 |
| BGP 路由表分析 | 通过 ASN 和路由前缀推断地理归属 |
| 主动测量 | 供应商自己的探针系统，持续 Ping 各 IP 段测延迟 |
| 用户反馈数据 | 根据实际访问效果持续校正 |

## 3.3 智能 DNS 的决策策略

根据不同需求，智能 DNS 可采用多种调度策略，往往组合使用：

### 3.3.1 地理位置就近（Geo-proximity）

最基本的策略：查询来自哪里，就返回那里最近节点的 IP。

```
查询来源 IP: 202.100.1.1 → 解析为"中国广东省电信"
最近 PoP: 香港节点（距离最近 + 跨境最快）
返回: 203.0.113.50
```

### 3.3.2 延迟最低（Latency-based）

GSLB 系统会主动探测（Ping/HTTP/TCP）各 PoP 到各地区的延迟，构建一个**延迟矩阵**，返回延迟最低的节点 IP，而非单纯的地理距离。

```
延迟矩阵示例（单位 ms）：
                欧洲用户  北美用户  东南亚用户
法兰克福 PoP:     15        80        200
洛杉矶 PoP:       80        10        180
新加坡 PoP:      210       185         20

→ 欧洲用户 → 法兰克福 PoP（15ms 最低）
→ 北美用户 → 洛杉矶 PoP（10ms 最低）
→ 东南亚用户 → 新加坡 PoP（20ms 最低）
```

### 3.3.3 健康状态感知（Health-aware）

GSLB 持续对每个 PoP 进行健康检查（HTTP 200 检测、TCP 连通性、响应时间阈值）。当某个节点故障时，自动从解析结果中剔除，防止用户被引导到不可用节点。

```
正常情况：
  东南亚用户 → 新加坡 PoP（IP: 43.0.1.1）

新加坡 PoP 故障（健康检查失败）：
  东南亚用户 → 香港 PoP（下一最近节点，IP: 203.0.113.50）
```

### 3.3.4 负载感知（Load-aware）

当某个 PoP 负载过高（CPU、带宽、连接数超阈值），智能 DNS 可以将部分查询调度到负载较低的备选节点，即使该节点延迟稍高。

### 3.3.5 运营商匹配（ISP-aware，中国特有）

在中国，由于电信、联通、移动三大运营商之间的互联成本高、质量差，智能 DNS 会精细到**按运营商**返回不同 IP：

```
查询来自中国电信用户 → 返回电信线路的 PoP IP
查询来自中国联通用户 → 返回联通线路的 PoP IP
查询来自中国移动用户 → 返回移动线路的 PoP IP
```

## 3.4 智能 DNS 的局限性

### 局限 1：依赖 Local DNS 的 IP（非用户真实 IP）

当用户使用第三方 DNS（如 8.8.8.8）时，GSLB 看到的是 Google DNS 的 IP，而非用户真实 IP，可能导致调度不准确。

**缓解方案**：EDNS Client Subnet（ECS）扩展，见第二章 2.6 节。

### 局限 2：TTL 缓存导致的调度延迟

一旦客户端或递归解析器缓存了某个节点的 IP，在 TTL 期间即使该节点故障也不会切换。

**缓解方案**：将 TTL 设为较小值（60～300 秒）；对于极端 HA 场景，结合应用层健康检查和重试机制。

### 局限 3：DNS 劫持风险

某些网络环境（特别是内网）存在 DNS 劫持，可能导致用户无法正确解析到供应商的 GSLB。

**缓解方案**：使用 DoH（DNS over HTTPS）或 DoT（DNS over TLS）加密 DNS 查询。

## 3.5 智能 DNS 与普通 DNS 的对比

| 特性 | 普通权威 DNS | 智能 DNS（GeoDNS） |
|------|------------|-------------------|
| 返回结果 | 所有请求相同 | 按来源 IP 动态不同 |
| 部署位置 | 单一或少量节点 | 全球多 PoP 部署 |
| 决策维度 | 无 | 地理/延迟/健康/负载/运营商 |
| 故障切换 | 手动修改记录 | 自动秒级切换 |
| TTL 建议 | 3600 秒+ | 60～300 秒 |
| 典型应用 | 普通网站 | CDN、全球加速、多活容灾 |

# 第四章：GSLB——全球服务器负载均衡架构

## 4.1 GSLB 概念与定位

GSLB（Global Server Load Balancing，全球服务器负载均衡）是在多个地理位置分布的数据中心之间进行流量调度的技术。与传统负载均衡器（在同一机房内分发请求到多台服务器）不同，GSLB 的视角是**全球范围内的多个站点（PoP）**。

```
传统负载均衡（SLB/LB）：
  用户 → 负载均衡器 → [服务器A, 服务器B, 服务器C]（同一机房）

GSLB（全局负载均衡）：
  用户 → GSLB DNS → [PoP-东京, PoP-法兰克福, PoP-纽约, PoP-香港]
                      ↓
                   选择最优 PoP → 该 PoP 内部 LB → [服务器1, 服务器2...]
```

## 4.2 GSLB 的实现方式对比

GSLB 有三种主要实现机制：

### 4.2.1 基于 DNS 的 GSLB（最主流）

**原理**：将智能 DNS 服务器部署为 GSLB 的决策层，在 DNS 解析环节就完成全局路由选择，将最优站点的 IP 地址返回给用户。

**优点**：
- 协议无关（TCP/UDP/HTTP 均适用）
- 对应用透明，无需修改客户端
- 天然支持 TTL 控制的缓存机制

**缺点**：
- 受 DNS TTL 缓存影响，故障切换有延迟
- 依赖 Local DNS IP 进行地理判断，精度有限

### 4.2.2 基于 HTTP 302 重定向的 GSLB

**原理**：用户先连接到一个"调度服务器"，调度服务器返回 302 重定向，将用户引导到最优节点。

**优点**：可根据真实用户 IP（非 DNS IP）做更精准的调度

**缺点**：增加一次 HTTP 往返（延迟），客户端必须支持重定向

### 4.2.3 基于 Anycast 的 GSLB

**原理**：多个 PoP 共享同一个 IP 地址，通过 BGP 路由协议让全球路由器将请求"就近"引导到最近的 PoP。

**优点**：对用户完全透明，BGP 天然实现就近路由

**缺点**：需要申请 BGP AS 号和 PI 地址段，成本高；主要用于 DNS 服务本身（如 1.1.1.1、8.8.8.8）和 DDoS 防护

## 4.3 基于 DNS 的 GSLB 详细工作机制

这是供应商最常用的模式，也是您的业务场景的核心机制。

### 4.3.1 GSLB 的 DNS 授权链

```
your-domain.com 的权威 DNS（域名注册商）
    ↓ 域名 CNAME 到供应商域名，或 NS 委托给供应商
供应商的 GSLB 权威 DNS
    ↓ 根据来源 IP 动态决策
返回最优 PoP 节点的 A 记录 IP
```

### 4.3.2 GSLB 内部决策流程

当 GSLB DNS 收到一个解析请求时，内部处理步骤如下：

```
1. 提取 DNS 查询信息
   - 查询域名: app.vendor-cdn.com
   - 来源 IP: 本地递归解析器 IP（或 ECS 中的用户 IP 前缀）

2. IP 地理定位
   - 查询 GeoIP 数据库
   - 结果: 来自德国法兰克福，运营商 Deutsche Telekom，ASN 3320

3. 候选节点筛选
   - 读取全局节点注册表
   - 剔除健康检查失败的节点
   - 筛选剩余健康节点: [法兰克福, 阿姆斯特丹, 伦敦, 马德里]

4. 最优节点评分
   - 地理距离权重: 法兰克福（10分）> 阿姆斯特丹（8分）> 伦敦（7分）
   - 延迟权重（来自 MEP 探测数据）: 法兰克福（12ms）最低
   - 负载权重: 法兰克福当前负载 65%，阿姆斯特丹 40%

5. 综合评分选择
   - 若法兰克福负载未超阈值（如 80%），选择法兰克福
   - 若超阈值，溢出到阿姆斯特丹

6. 返回 DNS 响应
   - A 记录: 151.100.1.50（法兰克福 PoP VIP）
   - TTL: 60
```

### 4.3.3 MEP（指标交换协议）：跨站点情报同步

GSLB 最关键的机制之一是各 PoP 节点之间**实时同步**健康状态和负载数据。商业 GSLB 系统（如 Citrix NetScaler、F5 BIG-IP DNS）使用专有的 **MEP（Metric Exchange Protocol）**：

```
各 PoP GSLB 节点每 5 秒互相推送：
  - 当前连接数
  - CPU/带宽利用率
  - 健康检查结果
  - 到各地区 Local DNS 的 RTT（往返时延）

任意一个 PoP 的 GSLB 在回答 DNS 查询时，
都能看到所有其他 PoP 的实时状态，从而做出全局最优决策。
```

## 4.4 GSLB 的健康检查体系

GSLB 需要实时掌握每个 PoP 和后端服务的健康状态：

| 检查类型 | 检查对象 | 频率 | 示例 |
|---------|---------|------|------|
| TCP 连通性 | PoP 入口 VIP | 每 5～10 秒 | TCP SYN 到 443 端口 |
| HTTP(S) 检查 | 应用层可用性 | 每 10～30 秒 | GET /health 期望 200 |
| RTT 测量 | 到各地区 LDNS 的延迟 | 持续（ICMP/UDP） | Ping 8.8.8.8 |
| 带宽利用率 | PoP 出口带宽 | 实时采集 | SNMP/Prometheus |
| 回源链路检查 | PoP → 中国源站专线 | 每 30 秒 | TCP 到源站端口 |

当健康检查连续失败（通常 3 次），该节点被标记为不可用，GSLB DNS 停止将其 IP 返回给任何用户。

## 4.5 GSLB vs 传统 CDN 的区别

您公司购买的"全球加速"方案并非纯 CDN（内容缓存），而是更接近"四层/七层代理 + 专线传输"的动态加速：

| 特性 | 传统静态 CDN | 全球动态加速（GSLB + 专线） |
|------|------------|--------------------------|
| 核心能力 | 边缘缓存静态资源 | 就近接入 + 专线回源 |
| 适用内容 | 图片/JS/CSS（可缓存） | API/动态请求（不可缓存） |
| 缓存命中率 | 高（70%～95%） | 0%（每次都回源） |
| 延迟优化来源 | 缓存命中（不回源） | 路径优化（骨干网替代公网） |
| 典型供应商 | 传统 CDN | 阿里云 GA、腾讯云 GAAP、Zenlayer |

# 第五章：CNAME 委托模型——为什么要 CNAME 到供应商域名

## 5.1 核心问题解答

**为什么供应商要求您将内网域名 CNAME 到他们的域名？**

答案很简单：**CNAME 是将 DNS 解析权"委托"给供应商的机制。** 只有当您的域名最终指向供应商的 DNS 服务器，供应商才能在 DNS 解析环节介入并进行智能调度。

## 5.2 CNAME 委托的工作原理

### 没有 CNAME 时（您自己控制 DNS）

```
员工/用户解析 app.corp.com
→ 您公司的权威 DNS 直接返回: A = 123.0.0.1 (中国源站 IP)
→ 用户直连中国源站
→ 问题：海外用户跨越公网，延迟高
```

### 加了 CNAME 委托后（供应商控制 DNS）

```
员工/用户解析 app.corp.com
→ 您公司的权威 DNS 返回: CNAME = app.your-account.vendor-cdn.com
→ 解析器继续查询 app.your-account.vendor-cdn.com
→ 供应商的 GSLB 权威 DNS 介入（这里是魔法发生的地方）
→ 供应商根据来源 IP 判断用户在哪里
→ 返回距离该用户最近的 PoP 节点 IP
→ 用户连接到最近的 PoP，PoP 经专线回国访问您的源站
```

## 5.3 CNAME vs NS 委托的区别

供应商接管 DNS 解析有两种方式，CNAME 是最常见、侵入性最低的：

| 方式 | 操作 | 侵入性 | 适用场景 |
|------|------|--------|---------|
| **CNAME（别名）** | 在您的 DNS 上加一条 CNAME 记录 | 低，只影响该条记录 | 单个域名/子域名加速 |
| **NS 委托** | 将整个子域的 NS 指向供应商 | 中，影响整个子域 | 整个子域名的全面管控 |
| **域名转入** | 把整个域名的权威 NS 换成供应商的 | 高，供应商全面接管 | 很少见，风险高 |

**为什么 CNAME 是正确选择：**
- 您的内网 DNS 仍然完全受您控制
- 只有 `app.corp.com` 这一条记录被"外包"给供应商解析
- 其他内部域名（`db.corp.com`、`jenkins.corp.com`）完全不受影响
- 随时可以删除 CNAME 记录，恢复直连模式

## 5.4 内网 DNS 的特殊性

您的场景有一个关键细节：您将**内网 DNS**（公司私有 DNS 服务器）上的记录 CNAME 到供应商。这意味着：

```
内网用户（在公司网络）:
  app.corp.com → CNAME → app.vendor-cdn.com
  → 递归解析 app.vendor-cdn.com
  → 供应商 GSLB 看到: 查询来自公司出口 IP（中国境内）
  → 返回: 中国本地节点 IP 或直连源站 IP（无需绕远路）

海外用户（远程访问 / VPN）:
  app.corp.com → CNAME → app.vendor-cdn.com
  → 递归解析时，供应商看到: 查询来自海外 IP
  → 返回: 海外最近 PoP 节点 IP
  → 连接 PoP → 经专线回国
```

> **关键点**：同一个域名，内网用户和海外用户得到的 IP 是不同的，这正是"智能"的体现。

## 5.5 CNAME 链条的完整解析示意

以下是一次完整的 DNS 解析过程（以海外用户为例）：

```
海外用户浏览器: "我要访问 app.corp.com"
  │
  ▼
操作系统 DNS 缓存
  │ (未命中)
  ▼
本地递归解析器（如 8.8.8.8 或 ISP DNS）
  │ 查询: app.corp.com
  ▼
您公司的权威 DNS（内网 DNS 或公网权威 DNS）
  │ 响应: app.corp.com CNAME app.your-account.vendor-cdn.com, TTL=300
  ▼
递归解析器: "好，现在要查 app.your-account.vendor-cdn.com"
  │ 查询: app.your-account.vendor-cdn.com
  ▼
供应商的 GSLB 权威 DNS（vendor-cdn.com 的权威服务器）
  │ 接收查询，判断逻辑:
  │   - 来源: 8.8.8.8 → 通过 ECS 获取用户IP前缀 → 判断: 德国法兰克福
  │   - 最近健康 PoP: 法兰克福节点（IP: 151.100.1.50）
  │   - 负载正常，决定调度到法兰克福
  │ 响应: app.your-account.vendor-cdn.com A 151.100.1.50, TTL=60
  ▼
递归解析器: 返回最终结果给用户
  app.corp.com → 151.100.1.50（法兰克福 PoP）
  ▼
用户浏览器: 建立 TCP 连接到 151.100.1.50
  ▼
法兰克福 PoP 接收连接，通过专线将请求转发到中国源站
```

## 5.6 供应商域名结构解析

供应商通常为每个客户分配专属的子域名，格式如：

```
<客户ID/账户名>.<产品线>.<供应商根域>
示例：
  your-account-123.ga.aliyuncs.com     （阿里云全球加速）
  your-account.gaap.tencentcloudapp.com （腾讯云 GAAP）
  abc12345.cdn.cloudflare.net           （Cloudflare CDN）
```

这个子域名是供应商 GSLB 系统的入口，它：
1. 标识您的账户（计费、配置查找）
2. 触发供应商 GSLB 的智能调度
3. 关联您配置的加速规则（目标源站 IP、协议、端口等）

## 5.7 为什么不直接给您一个固定 IP？

这是许多客户的另一个疑问：**为什么不直接给我一个固定 IP，让我 A 记录直接指向它？**

原因有三：

1. **固定 IP 无法实现地理调度**：不同地区用户需要连接到不同的 PoP，单一 IP 做不到（除非用 Anycast，但 Anycast IP 也需要 DNS 配合才能关联您的账户信息）。

2. **PoP 节点会扩容/迁移**：供应商随时可能增加新 PoP、调整 IP 段，CNAME 模式下您的配置无需改变，供应商在 GSLB 后端更新即可；固定 IP 则需要通知所有客户修改配置。

3. **多活容灾**：当某个 PoP 故障时，GSLB 可以将 DNS 解析切换到其他节点，而 IP 固定则意味着故障时用户无路可走。

## 6.3 阶段 1：DNS 解析阶段

```
时间轴: T+0ms

Alice 打开浏览器，输入 https://app.corp.com

Step 1.1: 本地 DNS 缓存检查
  Alice 电脑 DNS 缓存: 未命中 app.corp.com
  → 向本地 DNS 解析器发起查询（公司 DNS 服务器，通过 VPN 可达）

Step 1.2: 公司 DNS 响应（第一跳）
  公司内网 DNS: app.corp.com → CNAME app.acct123.vendor-ga.com, TTL=300
  注意: 公司 DNS 自身不知道 vendor-ga.com 的 IP，需要继续查

Step 1.3: 递归查询 vendor-ga.com
  本地递归解析器（公司 DNS 或 ISP DNS）:
  查询 app.acct123.vendor-ga.com 的 A 记录

  → 找到: vendor-ga.com 的权威 NS = gslb-ns1.vendor.com、gslb-ns2.vendor.com

Step 1.4: GSLB 权威 DNS 收到查询
  查询来源: 本地递归解析器（可能携带 ECS: 德国 IP 前缀）
  目标: app.acct123.vendor-ga.com

  【GSLB 内部决策（耗时约 1～5ms）】
  ① 账户识别: acct123 → 查找该账户的加速配置
  ② 地理判断: ECS 显示 德国法兰克福 → ASN: Deutsche Telekom
  ③ 节点筛选:
     - 法兰克福 PoP: 健康✓，负载 55%，预估延迟 12ms → 得分最高
     - 阿姆斯特丹 PoP: 健康✓，负载 70%
     - 伦敦 PoP: 健康✓，负载 40%，但距离稍远
  ④ 决策: 返回法兰克福 PoP 的 VIP IP

  GSLB 响应:
  app.acct123.vendor-ga.com  A  151.100.50.20  TTL=60

Step 1.5: 结果返回给 Alice
  Alice 的系统得到解析结果:
  app.corp.com → (CNAME app.acct123.vendor-ga.com) → 151.100.50.20
  DNS 解析总耗时: 约 20～50ms（含网络往返）
```

# 第七章：供应商内部架构——PoP 节点、骨干网与回源机制

## 7.1 供应商的核心资产

一个全球加速供应商的核心竞争力由三层组成：

```
┌─────────────────────────────────────────────────────┐
│  层1: 全球 PoP 节点网络（接入层）                    │
│  在全球主要城市部署接入点，就近接受用户连接           │
├─────────────────────────────────────────────────────┤
│  层2: 私有骨干传输网络（传输层）                     │
│  连接各 PoP 节点的高质量私有光纤/MPLS 网络           │
├─────────────────────────────────────────────────────┤
│  层3: 智能调度系统（控制层）                         │
│  GSLB + 健康检查 + 流量工程 + 计费系统              │
└─────────────────────────────────────────────────────┘
```

## 7.2 PoP 节点的内部构成

每个 PoP（Point of Presence，接入节点）通常部署在当地的互联网交换点（IXP）或数据中心，其内部架构如下：

```
                    ┌─────────────────────────────┐
                    │       法兰克福 PoP           │
                    │                             │
互联网入口           │  ┌─────────────────────┐   │
用户流量 ──BGP接入──►│  │   边缘路由器         │   │
(AS对等/Transit)    │  │  (BGP宣告 VIP 地址段)│   │
                    │  └──────────┬──────────┘   │
                    │             │               │
                    │  ┌──────────▼──────────┐   │
                    │  │   四层负载均衡(VIP)  │   │
                    │  │ (持有 151.100.50.20)│   │
                    │  └──────────┬──────────┘   │
                    │             │               │
                    │  ┌──────────▼──────────┐   │
                    │  │   七层代理集群        │   │
                    │  │  (TLS 终结/SNI路由)  │   │
                    │  │  (HTTP Header处理)   │   │
                    │  └──────────┬──────────┘   │
                    │             │               │
                    │  ┌──────────▼──────────┐   │
                    │  │  加速隧道出口        │   │
                    │  │ (GRE/IPsec/WireGuard)│   │
                    │  └──────────┬──────────┘   │
                    └────────────┼────────────────┘
                                 │ 供应商骨干专线
                                 ▼
                         供应商骨干网络
```

### 7.2.1 边缘路由器（BGP 接入）

PoP 通过 BGP 协议与当地 IXP 和上游运营商建立 BGP 对等（Peering）或购买 Transit，宣告本 PoP 负责处理哪些 IP 段（VIP 地址段）。全球路由器基于 BGP 最短路径，将目标 IP 为该 VIP 段的流量自动路由到最近的 PoP。

### 7.2.2 四层负载均衡（VIP 持有）

持有用户最终连接的 VIP（Virtual IP），基于 ECMP（等价多路径）或 consistent hashing 将 TCP/UDP 连接分发到后端七层代理集群。支持 DDoS 防护（流量清洗）。

### 7.2.3 七层代理（核心处理层）

这是 PoP 最重要的组件，承担：

| 功能 | 说明 |
|------|------|
| **TLS 终结** | 解密来自用户的 HTTPS 流量（持有您域名的 TLS 证书） |
| **SNI 路由** | 根据 TLS SNI 字段识别目标客户和目标服务 |
| **HTTP 处理** | 添加 `X-Forwarded-For`、`X-Real-IP` 等 Header |
| **协议转换** | 如 HTTP/2 → HTTP/1.1（向源站）；HTTPS → HTTP（内网） |
| **连接复用** | 与源站保持长连接池，避免每次请求重新建连 |
| **流量压缩** | gzip/brotli 压缩，减少骨干网传输量 |
| **健康检查** | 周期性检查回源链路和源站是否健康 |

### 7.2.4 加速隧道出口

PoP 通过供应商骨干网与其他 PoP 及中国接入点通信，常见封装协议：

- **GRE（Generic Routing Encapsulation）**：简单高效，供应商内部常用
- **IPsec**：加密传输，用于安全要求高的场景
- **WireGuard**：新一代高性能 VPN 协议，部分新供应商采用
- **MPLS**：运营商级专线，大型供应商的骨干网核心协议
- **SD-WAN**：软件定义广域网，灵活调度多条链路

## 7.3 供应商骨干网络

### 7.3.1 骨干网的本质

供应商骨干网是供应商自建或租用的、连接各 PoP 节点的**私有网络**，不经过公共互联网。其优势：

- **无拥塞**：容量按峰值设计，不与普通互联网流量竞争
- **SLA 保障**：供应商自己运维，可控制延迟和丢包率
- **优化路由**：供应商可以基于实测延迟选择最优路径，而非依赖 BGP 自动路由

### 7.3.2 全球骨干拓扑（典型结构）

```
北美西岸 PoP ────────── 北美东岸 PoP
     │                        │
     │（跨太平洋光缆）         │（跨大西洋光缆）
     │                        │
香港 PoP ────── 新加坡 PoP    欧洲枢纽 PoP
     │                        │
     │（跨境专线，合规）        │
     ▼                        │
中国接入点                中东/非洲 PoP
  └── 连接到各地区源站
```

核心枢纽往往是**香港**（连接中国大陆最方便）和**新加坡**（东南亚枢纽）。

### 7.3.3 智能路由（Traffic Engineering）

骨干网内部并非简单的固定路由，供应商会运行路由优化系统：

- **实时测量**：持续测量骨干网各链路的延迟和丢包
- **动态切换**：当某条路径拥塞时，自动将流量切换到备用路径
- **多路径并行**：对于高优先级流量，可同时走多条路径并取最快响应

## 7.4 回源机制详解

### 7.4.1 回源路径的建立

当 PoP 需要将请求转发到您的中国源站时，使用的是预先建立的专线隧道：

```
法兰克福 PoP
  │ (GRE 隧道 / MPLS 专线)
  ▼
供应商骨干网（欧洲段）
  │
  ▼
供应商香港 PoP（亚太枢纽）
  │ (跨境专线，须持有 ICP 和跨境数据许可)
  ▼
供应商中国接入点
  │ (与您源站建立的 TCP 连接池)
  ▼
您的源站 203.0.120.1:443
```

### 7.4.2 连接池（Connection Pooling）

PoP 不会对每个用户请求都向源站新建 TCP+TLS 连接（开销极大）。而是维护一个**连接池**：

```
连接池工作机制:
- PoP 与源站预先建立 N 条 TCP/TLS 长连接（如 100 条）
- 用户请求到来时，从池中复用一条连接，发送 HTTP 请求
- 响应返回后，连接归还回池
- 池中连接超时空闲则关闭，不足时按需新建

优势:
- 避免每次请求的 TCP+TLS 握手开销（节省 100～300ms）
- 减少源站的连接数压力
```

### 7.4.3 回源协议和 Header

PoP 向源站发出的请求会携带原始用户信息：

```http
GET /api/user/profile HTTP/1.1
Host: app.corp.com
X-Forwarded-For: 83.100.200.1        ← 原始用户 IP（德国）
X-Real-IP: 83.100.200.1
X-Forwarded-Proto: https
X-Vendor-PoP: frankfurt-01            ← 供应商添加，标识接入节点
True-Client-IP: 83.100.200.1
```

您的源站通过 `X-Forwarded-For` 可以获取真实用户 IP，用于日志、风控等场景。

## 7.5 供应商的 GSLB 控制平面

GSLB 控制平面是供应商最核心的"大脑"，由以下组件构成：

| 组件 | 职责 |
|------|------|
| **GeoIP 数据库** | IP → 地理位置/运营商 映射 |
| **健康检查引擎** | 周期性对各 PoP 和源站做存活探测 |
| **延迟探测系统** | 实时测量各 PoP 到各地区 LDNS 的 RTT |
| **节点状态同步（MEP）** | 各 PoP 实时互推健康状态和负载数据 |
| **DNS 服务器集群** | 接收全球 DNS 查询，执行智能解析 |
| **调度策略引擎** | 综合地理/延迟/负载/健康，计算最优节点 |
| **配置管理系统** | 存储各客户账户的加速规则、源站配置 |
| **计量计费系统** | 统计各账户的流量、连接数、延迟等指标 |

## 7.6 故障场景处理

### 场景1：单个 PoP 故障

```
检测: 法兰克福 PoP 健康检查失败（连续3次）
处理:
  1. GSLB 标记法兰克福 PoP 为 DOWN
  2. 将法兰克福 PoP 的 IP 从 DNS 响应中移除
  3. 对德国用户，改为返回阿姆斯特丹 PoP 的 IP
  4. 等待法兰克福恢复后，重新纳入服务（fail-back）
用户感知: 在 DNS TTL 期间（60s内）可能感受到切换延迟
```

### 场景2：供应商骨干链路故障

```
检测: 法兰克福 → 香港 骨干链路丢包率 > 5%
处理:
  1. 流量工程系统自动启用备用路径（如法兰克福 → 美西 → 香港）
  2. 或启用 SD-WAN 备用链路
  3. 必要时降级通过公网（质量下降但不中断）
用户感知: 可能短暂延迟增加，基本无感知
```

### 场景3：源站故障

```
检测: PoP 向 203.0.120.1 的健康检查失败
处理:
  1. 停止向该源站转发请求
  2. 如配置了备用源站，切换到备用
  3. 向客户（您）发送告警通知
  4. 对用户返回配置的错误页面（如 502 或自定义维护页）
```

# 第八章：中国特殊性——ICP 合规、多运营商与跨境专线

## 8.1 中国网络环境的特殊性

中国的互联网环境与全球其他地区有根本性不同，这也是为什么"全球加速回中国"是一个独立的专项产品。

### 8.1.1 跨境互联带宽瓶颈

```
全球互联网 ←→ 中国互联网 的连接通过有限的几个"出入口"：

主要国际出口点:
  - 上海: 中国电信、中国联通的核心出口
  - 北京: 中国教育网、移动的出口
  - 广州: 华南地区核心出口
  - 香港: 最常用的中转点（物理距离近，有多条海缆）

问题: 这些出口带宽总量相对全球流量需求是不足的
      每逢晚间高峰期，国际出口拥塞，公网延迟和丢包急剧上升
```

### 8.1.2 三大运营商互联问题

中国三大运营商（电信、联通、移动）之间的流量互通需要经过骨干互联点（NAP），互联带宽有限，跨运营商访问质量差：

```
典型问题:
  联通用户 → 访问电信机房的服务器 → 需经过运营商互联点 → 延迟大
  
传统解决方案: 双线/多线机房（同时接入电信和联通出口）
全球加速方案: PoP 就近接入用户 → 供应商骨干网（无运营商障碍）→ 回源
```

### 8.1.3 防火长城（GFW）对流量的影响

部分协议和境外 IP 可能受到流量检测和限速，全球加速供应商通常：
- 使用合规的跨境专线（而非普通互联网路由）
- 持有必要的电信经营许可证（跨境数据业务许可）
- 协议层面使用标准 TLS，不使用混淆协议

## 8.2 ICP 许可证与合规要求

### 8.2.1 什么是 ICP 备案

在中国境内提供互联网信息服务的网站必须持有：

| 证件类型 | 适用场景 | 发放机构 |
|---------|---------|---------|
| **ICP 备案** | 非经营性网站（展示型） | 工信部（通过运营商申请） |
| **ICP 许可证** | 经营性网站（电商、服务） | 工信部 |
| **跨境数据业务许可** | 供应商经营跨境数据传输 | 工信部 |

### 8.2.2 对供应商的合规要求

您选择的全球加速供应商（若其在中国境内有接入点）必须持有：
- **增值电信业务许可证（IDC/CDN/ISP）**：允许在境内提供数据传输服务
- **跨境专线许可**：允许建设和运营跨境数据电路

**这也是为什么您不能自己随便搭一个 VPN 服务器来解决这个问题**——使用未授权的跨境通道在中国是违规的，只有持牌供应商才能合法经营跨境数据传输业务。

### 8.2.3 您的内网域名不需要 ICP 备案吗？

通常情况下：
- **仅供内部员工访问的内网系统**：不需要 ICP 备案（非公开面向公众）
- **对外部用户/合作伙伴开放的系统**：视情况可能需要

实际操作中，许多跨国企业将全球加速方案定位为"企业专线"（B2B），而非公众互联网服务，因此合规判断有所不同。建议咨询您的供应商和法务团队。

## 8.3 中国境内的接入点设计

供应商在中国境内通常有以下几类接入架构：

### 8.3.1 境内 PoP + 骨干专线模式

```
海外用户 → 海外 PoP → 骨干专线 → 供应商境内接入点 → 您的源站

供应商境内接入点: 位于上海/北京/广州等核心数据中心
特点: 供应商直接持有境内服务器，合规性高
```

### 8.3.2 Hong Kong 中转模式（常见）

```
海外用户 → 海外 PoP → 骨干专线 → 香港 PoP → 跨境专线 → 您的源站

香港特点:
- 不受大陆 GFW 影响
- 多条海底光缆（PCCS、SMW3、APG 等）连接全球
- 到大陆的专线延迟约 5～15ms
- 许多供应商选择香港作为"进出中国"的枢纽
```

### 8.3.3 云上骨干网模式（阿里云、腾讯云等）

```
海外用户 → 海外 PoP → 云厂商全球骨干 → 云厂商中国 Region
                                          → 您的 ECS/SLB（云上源站）

特点: 源站在云上，供应商和源站同属一家云厂商，专线完全自有
      延迟最低，管控最严，也最贵
```

## 8.4 运营商多线智能调度

当您的源站在中国境内接入了多条运营商线路（或使用了 BGP 多线机房），供应商的 GSLB 可以进一步按运营商优化回源路径：

```
用户来自中国电信 → 海外PoP → 骨干网 → 从电信出口回源 → 您的电信服务器IP
用户来自中国联通 → 海外PoP → 骨干网 → 从联通出口回源 → 您的联通服务器IP
用户来自中国移动 → 海外PoP → 骨干网 → 从移动出口回源 → 您的移动服务器IP
```

实际上，由于您使用了供应商的全球加速方案，通常源站侧已不需要多线接入——供应商在其中国接入点处已经处理了运营商多线问题。

## 8.5 数据安全与合规考量

### 8.5.1 流量经过第三方 PoP 的安全考量

由于 TLS 在 PoP 处终结，供应商理论上可以看到解密后的 HTTP 明文流量（除非使用了 mTLS 端到端加密）。

**应对措施**：
- 要求供应商签署 NDA 和数据处理协议（DPA）
- 选择有 ISO 27001、SOC2 认证的供应商
- 对特别敏感的接口（如含个人信息的 API）使用 mTLS（双向证书认证）
- 要求供应商提供流量日志访问权限，便于审计

### 8.5.2 数据本地化要求

部分行业（金融、医疗、政府）有数据不出境要求。全球加速方案的流量会经过境外 PoP，**不适用于此类数据**。这类场景应使用纯境内方案或 SD-WAN 企业专线（不经过境外节点）。

### 8.5.3 中国个人信息保护法（PIPL）

2021 年起实施的 PIPL 对个人信息跨境传输有严格要求：
- 向境外传输中国用户个人信息需要满足安全评估/标准合同/认证之一
- 全球加速方案中，如果用户请求中包含中国用户个人信息并被传到境外 PoP，需要评估合规性

**建议**：与法务团队确认您的业务数据是否涉及个人信息，以及是否适用 PIPL 要求。

# 第九章：总结与常见问题

## 9.1 核心原理总结

经过前八章的详细分析，我们可以将整个全球加速方案的工作原理归纳为以下核心逻辑：

### 9.1.1 五层架构模型

```
┌──────────────────────────────────────────────────────────────┐
│  层1: DNS 解析层（CNAME + GSLB）                             │
│  功能: 将用户引导到最近的 PoP 节点                           │
│  关键: 智能 DNS 根据来源 IP 返回不同节点 IP                  │
├──────────────────────────────────────────────────────────────┤
│  层2: PoP 接入层（就近接入）                                 │
│  功能: 在用户所在地区终结 TCP/TLS 连接                       │
│  关键: 最小化用户到第一跳的延迟（本地延迟 <20ms）            │
├──────────────────────────────────────────────────────────────┤
│  层3: 骨干传输层（私有专线）                                 │
│  功能: PoP 之间通过高质量私有网络传输                        │
│  关键: 绕过拥塞的公网，使用可控的私有骨干                    │
├──────────────────────────────────────────────────────────────┤
│  层4: 跨境接入层（合规专线）                                 │
│  功能: 合法跨越中国边界，连接境内网络                        │
│  关键: 供应商持有电信许可证，走合规专线                      │
├──────────────────────────────────────────────────────────────┤
│  层5: 源站服务层（您的服务器）                               │
│  功能: 处理实际业务请求，返回数据                            │
│  关键: 无需改造，正常监听即可                                │
└──────────────────────────────────────────────────────────────┘
```

### 9.1.2 一句话总结

> 智能 DNS（GSLB）把用户引导到最近的 PoP，PoP 在本地完成 TCP/TLS 握手，再经供应商私有骨干网低延迟传输到中国源站——用"就近接入 + 专线传输"替换"全程公网直连"。

## 9.2 为什么 CNAME 是整个方案的钥匙

```
没有 CNAME → 用户直接解析到源站 IP → 全程公网 → 延迟高
有了 CNAME → 解析交给供应商 GSLB  → 就近 PoP + 专线 → 延迟低

CNAME 的作用 = 将 DNS 解析控制权委托给供应商
              = 供应商获得了在用户访问前就做出路由决策的能力
```

## 9.3 常见问题解答（FAQ）

### Q1：为什么我内网用户也 CNAME 了，但他们访问速度没变？

**答**：这是正确的行为。供应商的 GSLB 检测到查询来自中国境内 IP，会返回您源站的直达 IP 或中国本地节点 IP，内网用户不会被绕道经过海外 PoP。你可以让供应商配置"中国来源请求直连源站"策略。

---

### Q2：如果供应商的 GSLB DNS 宕机了，我们是否会完全中断？

**答**：存在风险。缓解措施：
1. 将 CNAME 记录的 TTL 设为 300 秒，使 DNS 缓存能撑过短暂故障
2. 要求供应商提供 GSLB 的 SLA（通常 99.99%+）
3. 配置备用解析（如 DNS 健康检查 + 主备切换）：当供应商域名不可达时，将 CNAME 改回直连源站 A 记录

---

### Q3：全球加速对 WebSocket / 长连接有影响吗？

**答**：通常没有负面影响，反而有优化。PoP 层面维护与用户的长连接，并将流量通过连接池传递给源站，源站处的连接数大幅减少。但需确认供应商的 PoP 支持 WebSocket 协议（七层代理层面需要配置 `Connection: Upgrade` 穿透）。

---

### Q4：我的 DNS 是内网 DNS（Split DNS），海外远程员工如何访问？

**答**：Split DNS 场景下，海外员工需要能访问到您的内网 DNS 服务器，通常通过 VPN 实现。典型架构：
- 员工连接公司 VPN
- VPN 分配内网 DNS 地址
- 员工解析 `app.corp.com` → 内网 DNS 返回 CNAME → 供应商 GSLB 介入
- 因为员工连着 VPN，其 DNS 查询来源 IP 可能是 VPN 集中器的 IP

**注意**：如果 VPN 集中器在中国境内，员工的 DNS 来源 IP 是中国 IP，GSLB 会返回中国节点，等同于内网用户。这种情况下海外员工实际上是：
- VPN 连接路径：员工 → VPN 隧道（经公网）→ 中国 VPN 集中器
- 应用访问路径：中国 VPN 集中器代理请求 → 源站

这时全球加速方案未能发挥作用（VPN 本身已承担了跨境流量）。需要与供应商讨论"Split DNS + 非 VPN 远程访问"的方案。

---

### Q5：CNAME 到供应商会不会有安全风险？

**答**：主要风险和应对：

| 风险 | 说明 | 应对 |
|------|------|------|
| TLS 流量在 PoP 被解密 | 供应商理论上可见明文 | 签署 DPA，使用 mTLS |
| 供应商账户被盗 | 攻击者可修改回源配置 | 启用 MFA，审计变更 |
| DNS 劫持 | 攻击者替换 CNAME 目标 | DNSSEC，监控 DNS 记录 |
| 供应商倒闭/停服 | CNAME 无法解析 | 保持备用直连 A 记录，演练切换 |

---

### Q6：TTL 设置多少合适？

**答**：

| 场景 | 建议 TTL |
|------|---------|
| 正常运营 | 60～300 秒（推荐 60）|
| 计划变更前 | 提前 48 小时改为 60 秒 |
| 紧急故障切换 | 越小越好（但受已缓存值影响）|
| 内网 DNS 记录 | 300 秒（内网 DNS 通常不缓存很久）|

---

### Q7：全球加速和传统 CDN 有什么区别？我们的场景该用哪个？

**答**：

| 方案 | 适合场景 | 不适合场景 |
|------|---------|-----------|
| 传统 CDN | 静态资源（图片/JS/CSS）全球分发 | 动态 API、实时数据 |
| 全球动态加速（GA） | 动态内容、API、WebSocket、实时服务 | 纯静态资源（CDN 更便宜） |
| 两者结合 | 静态资源走 CDN，动态请求走 GA | — |

**您的场景**（访问中国内网系统）适合使用**全球动态加速**，因为内网系统的内容是动态的，无法缓存。

## 9.4 实施检查清单

在您正式上线前，建议确认以下事项：

### DNS 配置检查
- [ ] 内网 DNS 上已创建 CNAME 记录，指向供应商提供的域名
- [ ] CNAME 记录 TTL 已设置为合理值（建议 60 秒）
- [ ] 已在供应商后台配置源站 IP 和端口
- [ ] 已测试：内网用户解析域名得到正确 IP
- [ ] 已测试：模拟海外来源（使用 dig @8.8.8.8）得到 PoP IP

### 连通性测试
- [ ] 海外网络（模拟）可访问供应商 PoP IP
- [ ] PoP 可正常连通您的源站
- [ ] 端到端 HTTPS 连接测试通过
- [ ] WebSocket / 长连接测试（如适用）

### 性能基线
- [ ] 记录未加速前的延迟基线（各大洲 P50/P95）
- [ ] 上线后对比延迟改善效果
- [ ] 确认丢包率在可接受范围

### 安全与合规
- [ ] 供应商已签署 NDA / DPA
- [ ] TLS 证书已配置（供应商托管或自有证书上传）
- [ ] 供应商提供的合规证书（ICP 许可、ISO 27001 等）已存档
- [ ] 已评估 PIPL 合规性（如涉及中国用户个人信息出境）

### 容灾准备
- [ ] 已准备好备用直连 A 记录（供供应商故障时快速切换）
- [ ] 已演练从 CNAME 切换到直连 A 记录的操作流程
- [ ] 监控和告警已配置（供应商宕机告警、延迟告警）
